Sehat Ledger — Master Build Prompt
How to use this on 26 July. Do NOT paste the whole thing in one go and accept a finished app — a hackathon judges "progress made today" at 25%, and a single mega-prompt leaves no visible build trail. Feed it to the LLM phase by phase (they are numbered below). Commit after each phase with a real message. That way the git history shows genuine building, the app is identical to what you have now, and every claim you make to a judge is true.

Everything below the line is the prompt. Paste the Context block first, then Phase 1, work through to Phase 8.

CONTEXT BLOCK — paste this first, every session
You are building Sehat Ledger, an offline-first Progressive Web App for a real NGO, the Active Bengaluru Foundation (ABF). It is used by volunteers at mosque-based health screening camps in Bengaluru to screen people for diabetes and hypertension, generate multilingual referrals, chase those referrals to completion, and measure the community care burden deferred — expressed in rupees of zakat preserved.

The one-line thesis: community zakat funds are consumed by late-stage dialysis and cardiac care that early screening at ₹12–15 per person could have prevented. One dialysis patient costs ₹1,58,880/year in community support — the same money screens ~10,600 people. The app turns every confirmed referral into a measurable rupee figure a mosque treasurer can act on.

Hard architectural constraints — do not violate these
No build step. No framework. No bundler. No npm. Plain HTML, one CSS file, and ES modules loaded natively by the browser via <script type="module">. This is deliberate: it must be fixable by editing a file and refreshing, and deployable by git push to GitHub Pages.
No external libraries at all. No React, no Supabase JS client, no charting library, no icon package. Everything is hand-written fetch(), DOM APIs, and inline SVG.
Offline-first. Every screening must complete with zero connectivity. Patient data is written to localStorage first, always. The network is never in the critical path.
The only network calls are: (a) LLM calls for vision/text, made only when a reading is captured or a button is pressed; (b) optional Supabase sync over plain REST. Both degrade gracefully to fully-local operation.
Dark, glassmorphic UI. Black canvas, one brand yellow #FFD140 reserved strictly for primary action / selection / progress / focus. Clinical status uses a separate colour band (emerald / amber / rose) so "at risk" can never be confused with "tap this."
This is screening, NOT diagnosis. No condition is ever named to a patient. No medication advice is ever generated. Every output routes to "see a doctor about this."
File structure (create exactly these)

styles.css                 design system, ~1100 lines
app.js                     routing, screening flow, all views, rendering
clinical.js                pure scoring functions (IDRS, BMI, BP, glucose)

manifest.webmanifest       PWA manifest

Navigation — five views, tab-based
Screen (new screening wizard) · Records · Follow-up · Ledger · Settings. Desktop: 248px sticky left sidebar. Mobile (≤900px): sidebar becomes a fixed bottom tab bar, and a compact top header carries the logo + avatar.

PHASE 1 — Clinical engine (clinical.js)
Pure functions only. No DOM, no network, no state. Every threshold traces to a published instrument — never invent scoring. Export everything.

BMI — Asian Indian (ICMR) cut-offs, NOT standard WHO
< 18.5   underweight   (tone: warn)
< 23.0   normal        (tone: ok)      // note: healthy range
< 25.0   overweight    (tone: warn)
>= 25.0  obese         (tone: high)
calcBMI(heightCm, weightKg) returns kg/(m²) rounded to 1 decimal, or null if either input missing. classifyBMI(bmi) returns {value, key, label, tone, note} with note "Asian Indian cut-offs (ICMR). Lower than standard WHO thresholds."

Blood pressure — ACC/AHA categories
sys>=180 OR dia>=120  crisis   critical  "Same-day medical attention. Do not send home with a routine slip."
sys>=140 OR dia>=90   stage2   high      "Clinician review needed."
sys>=130 OR dia>=80   stage1   warn      "Repeat reading and clinician review."
sys>=120              elevated warn      "Recheck in 3 months."
else                  normal   ok        "Routine recheck in 12 months."
classifyBP(systolic, diastolic) returns null if either is 0/missing, else {systolic, diastolic, key, label, tone, action}.

Capillary glucose (mg/dL)
fasting:  >=126 diabetes/high · >=100 impaired/warn · else normal/ok
random:   >=200 diabetes/high · >=140 raised/warn   · else normal/ok
classifyGlucose(mgdl, fasting) returns {value, fasting, key, label, tone, note} with note "Capillary screening value. Venous confirmation required before any diagnosis."

IDRS — Indian Diabetes Risk Score (Mohan et al., MDRF, 2005), 0–100
Four components:

Age: ≥50 → 30, ≥35 → 20, else 0
Waist (cm): female thresholds 80/70, male 90/80. ≥higher → 20, ≥lower → 10, else 0
Physical activity: vigorous 0, moderate 10, mild 20, sedentary 30 (default mild=20)
Family history of diabetes: both parents 20, one 10, none 0
Bands: ≥60 high/high · ≥30 moderate/warn · else low/ok.

Waist fallback: if no waist measurement, derive from BMI (≥25 → 20 pts, ≥23 → 10 pts, else 0) and set proxied: true on the result. Never silently swap the input — flag it.

calcIDRS({age, sex, waistCm, bmi, activity, family}) returns {total, band, label, tone, proxied, components:[{name, points, max, proxied?}]}.

Overall outcome — measured vitals always dominate the questionnaire
assess(record) runs all of the above and escalates to the highest of four outcomes:

urgent  — BP crisis
refer   — BP stage2, glucose diabetes range, or IDRS high
monitor — BP stage1, glucose impaired, IDRS moderate, BMI obese, or already-diagnosed
routine — nothing raised
Escalation is monotonic (rank routine<monitor<refer<urgent; only ever raise). Collect a reasons[] array of plain-language strings for each trigger. Return {bmi, bp, glucose, idrs, outcome, reasons, ...OUTCOME_META[outcome]}.

OUTCOME_META maps each outcome to {title, tone, summary, followUp, referral}:

urgent: "Needs care today" / critical / referral+followUp true
refer: "Refer to clinician" / high / referral+followUp true
monitor: "Monitor" / warn / both false
routine: "Routine recheck" / ok / both false
Ramadan fasting risk — IDF-DAR categories
fastingRisk(record, assessment) returns null unless the person is diabetic (known or glucose in diabetes range). Otherwise grades veryhigh/high/moderate from: on insulin, glucose ≥300, hypo history, CKD (→ veryhigh); sulfonylurea, age ≥70 (→ high). Returns {level, factors[], label, tone, guidance, disclaimer}. Disclaimer must state: clinical guidance only, grounded in IDF-DAR; religious rulings on exemption rest with a qualified scholar, not the app.

Write a small test harness (Node, --input-type=module) asserting: BMI 170/70 = 24.2 and classifies overweight; BP 185/125 = crisis; IDRS max case (age55/waist95/sedentary/both) = 100; measured BP crisis beats a low questionnaire. This proves the engine before any UI exists.

PHASE 2 — Zakat ledger model (ledger.js)
Every assumption is a named, editable constant, surfaced in the UI later. Two are observed from ABF field data; three are conservative assumptions, labelled as such.

ASSUMPTIONS = {
  annualBurden:       { value: 158880, unit: '₹/year', observed: true,
                        label: 'Annual support per dialysis patient',
                        source: 'ABF committee disbursement records, Bengaluru, 2026' },
  screeningCost:      { value: 15, unit: '₹', observed: true,
                        label: 'Consumables per screening',
                        source: 'ABF field costing. Range ₹12–15; upper bound used.' },
  progressionHigh:    { value: 0.020, observed: false,
                        label: 'Annual progression to high-cost complication, high risk' },
  progressionModerate:{ value: 0.008, observed: false,
                        label: 'Annual progression, moderate risk' },
  interventionEffect: { value: 0.50, observed: false,
                        label: 'Share of progression averted by early management' }
}
Deferred per confirmed case = annualBurden × P(progression/yr) × interventionEffect, using progressionHigh for outcomes urgent/refer, progressionModerate for monitor, 0 otherwise. Single-year horizon only — do not multiply across years; that would quintuple every figure and collapse under scrutiny.

The load-bearing rule: ledger credit is written only when a referral's status is confirmed (i.e. the follow-up agent confirmed the person reached a doctor). A referral merely issued is never counted. Track pending referrals and their potential value separately.

computeLedger(records, overrides) returns: screened, flagged, referralsIssued, referralsConfirmed, pendingFollowUp, completionRate, byOutcome{}, spend (=screened×cost), deferred (confirmed only), deferredPending, dialysisYearsEquivalent (=deferred/annualBurden), screeningsFundedByOneDialysisYear (=round(annualBurden/cost)), assumptions.

Add formatINR (Indian grouping, e.g. ₹1,58,880) and formatCompactINR (₹1.5 L / ₹2 Cr). getAssumptions(overrides) merges saved overrides over defaults.

Test: one dialysis year ÷ ₹15 = 10,592 screenings; per-high-risk-case = ₹1,588.80; exactly 100 confirmed high-risk cases = one dialysis year; pending referrals excluded from deferred.

PHASE 3 — AI layer (ai.js)
Three model capabilities, each with a deterministic mock fallback and multi-provider failover. Structured JSON output throughout.

Providers & routing
Primary: Google Gemini (gemini-flash-latest), REST: POST generativelanguage.googleapis.com/v1beta/models/{model}:generateContent?key=… with responseSchema and responseMimeType: application/json.
Fallback: OpenRouter (OpenAI-compatible, openrouter.ai/api/v1/chat/completions), free vision models. Convert Gemini parts to OpenAI content blocks (text / image_url data-URI). Use response_format: json_object plus the schema described in the system prompt.
callModel({parts, schema, system, temperature}) tries providers in configured order (default gemini,openrouter). Move to the next provider only on rate-limit/transient errors (429/503/500, or /quota|rate.?limit|exhausted|overloaded/). A genuine bad request fails fast. If every provider is exhausted or unconfigured, the caller falls to a mock.
Keys in localStorage: sl.apiKey/sl.model (Gemini), sl.orKey/sl.orModel (OpenRouter). configuredProviders() returns those with keys.
listOpenRouterModels() queries /models and filters to free + image-capable — never hardcode a model list, names churn.
testConnection() (Gemini) and listModels() for the Settings connection test.
1. readDeviceScreen(base64, mime) — vision
System prompt: reads numeric displays on glucometers (single number, mg/dL in India), BP monitors (larger=systolic over diastolic, plus pulse), digital scales. Report only digits actually visible — never infer, never complete a partial number, never guess a plausible clinical value. If blurred/glare/angled/off, set confidence low and leave numeric fields null. A refusal is safer than a wrong vital. Schema: {deviceType, glucose?, systolic?, diastolic?, pulse?, weightKg?, unit?, confidence, note}. Mock returns a labelled simulated glucometer or BP reading.

2. generateReferral({record, assessment, language, facility, scheme}) — multilingual slip
System prompt: writes referral slips for people with limited literacy, read once at home. NEVER name a diagnosis, NEVER mention/adjust medication. Short everyday sentences. Direct about urgency without alarm. Diet advice specific to how people here eat (rice, chapati, sweet tea, biryani, dates/sherbet at iftar) — "reduce carbohydrate intake" is banned. Write in the target language and its own script. Schema: {headline, body, whatToSay (exact words for the clinic desk), dietNote, urgencyNote?, englishGloss}. Mock returns a labelled simulated slip.

3. followUpTurn({record, assessment, thread, language, facility, scheme, dayIndex}) — the agent
System prompt: contacts the patient a few days post-referral. Never diagnoses, never prescribes. Never repeats a reminder — if they haven't gone, find the specific obstacle and address it. Assume a practical barrier (work, timing, cost, location, fear) before apathy. Warm, brief, WhatsApp register, their language. Stop if asked. After two unanswered messages, escalate to the volunteer. Schema: {barrier (enum), reply, englishGloss, action (await_reply|resolve_barrier|escalate_to_volunteer|mark_confirmed|stop), actionDetail, referralStatus (pending|confirmed|declined)}. Barriers enum: went, location_unknown, timing_conflict, cost_concern, transport, low_severity, fear, no_response, declined, unclear. Mock branches on keywords in the last patient message (work→timing, money→cost, where→location, "went"→confirmed, etc.).

Every function: on NO_KEY return the mock silently; on real error return the mock with an error field and set status. Expose AI_STATUS, getLastStatus(), getLastProvider(), hasKey(), BARRIERS.

Shell (index.html)
<!doctype html>, dark theme-color, PWA meta, manifest + apple-touch-icon links, preload the font. Storage & helpers (app.js)

Helpers: $/$$, esc (HTML escape), uid, initials, toast, sheet/closeSheet, an ICON map of inline SVG strings, scrollTop() and focusField(sel,msg) (blur active element first, scroll into view, focus with preventScroll — respect reduced motion).

Screening wizard — 4 steps, one draft object
Steps labelled Consent · Risk factors · Measurements · Summary. Keep a draft object and step index; renderedStep tracks the last rendered step so scroll-to-top fires only on an actual step change (not on every re-render). Each step renders into cards + a pinned action row.

Step 0 — Consent & identity: a consent quote box (the exact script read aloud); two toggles — Consent given for screening (blocks progress if off) and Consent to follow-up messages (optional, separate). Consent script: "We would like to check your blood pressure, blood sugar, height and weight. There is no charge. Your results are shared only with the health programme and the doctor we refer you to. You can stop at any time and you do not have to answer anything you do not want to." Then: name, mobile, age, sex (segmented M/F), centre (select), language (select: Urdu, Kannada, Hindi, Tamil, English). Validation jumps to the failing field.
Step 1 — Risk factors: physical activity (4-way segmented), family history (3-way), waist cm (optional, hint that BMI proxy is used + flagged if blank). Existing-conditions toggle card: known diabetic, known hypertensive, insulin, sulfonylurea, tobacco.
Step 2 — Measurements: a "Read the device" capture card (camera), then BP (sys/dia), glucose (mg/dL) + random/fasting segmented, height, weight. Camera: getUserMedia({facingMode:environment}) with live viewfinder + capture; fallback to <input capture=environment> when getUserMedia is unavailable (needed on non-HTTPS). On capture, call readDeviceScreen, show a scanning overlay, then animate the returned digits into the matching fields (.landed animation, green "filled" state). Low confidence → a "couldn't read it, enter by hand" notice.
Step 3 — Summary/result: run assess(draft). Show an outcome hero (toned by severity), a vitals grid (BP/glucose/BMI tiles with labels), the IDRS breakdown (component bars + total badge + proxied note), a reasons list, and the Ramadan fasting card if applicable. A closing screening-not-diagnosis disclaimer. Primary button: "Generate referral" (if outcome needs one) else "Save record".
Finish: on save, stamp outcome/idrsTotal onto the draft and upsert. If referral needed: call generateReferral with the centre's facility, render the slip (scroll it into view), set referralIssued:true, referralStatus:'pending'; if follow-up consent + phone given, mark followUpDue. Reference data: 5 CENTRES, a FACILITIES map (centre → {name, hours}), SCHEME = "Ayushman Bharat Arogya Karnataka", LANGUAGES, RTL = ['Urdu'].

Binders: bindInputs (write to draft on input), bindSeg (segmented), bindSwitch (toggles), toggleRow helper.

PHASE 7 — Offline + PWA (sw.js, manifest.webmanifest, icon.svg)
sw.js: cache-first for the app shell (list every file: html, css, all js incl. sync.js, icon, manifest, logo, both bg images, font). install → cache.addAll(SHELL) then skipWaiting; activate → delete old caches + claim; message handler for skipWaiting. fetch: never cache generativelanguage.googleapis.com or *.supabase.co; cache-first with background refresh for same-origin GETs; fall back to index.html. Bump the cache version string on every deploy. Critical: if any file in the shell list 404s, cache.addAll rejects atomically and offline dies silently — the file list must be exact.
Self-updating worker (in app.js): register with updateViaCache:'none', call reg.update() on load, postMessage('skipWaiting') when a new worker installs, reload once on controllerchange. A cache-first worker serving yesterday's JS looks exactly like "my changes did nothing."
manifest.webmanifest: name, short_name "Sehat Ledger", standalone, portrait, dark theme/background, icon.svg (any + maskable), shortcuts to Screen and Ledger.
icon.svg: yellow rounded square, coral heart, yellow ECG pulse line through it.
PHASE 8 — Shared sync (sync.js) — build last, keep optional
Local-first sync to Supabase over plain REST (PostgREST) — no client library. Table records(id text pk, updated_at timestamptz, data jsonb).

Config in localStorage (sl.sbUrl, sl.sbKey). isConfigured(), setConfig(), a listener/emit pattern, status().
Push: POST dirty records with Prefer: resolution=merge-duplicates; clear _dirty only on success.
Pull: GET ordered by updated_at; merge last-write-wins except a locally dirty record always beats the server (it holds unsent edits).
syncNow({read, save}), startSync (poll every 12s + on visibilitychange + on online), stopSync. Local write always succeeds first — sync is never in the critical path.
testConnection() (probes the table, explains 404 = run SQL, 401/403 = key/policy). SETUP_SQL string creating the table + index + RLS + an open demo policy (using(true)), surfaced in the UI with a copy button.
Setup link: makeSetupLink() base64url-encodes {u,k,g,m,o,om} (Supabase + both AI keys) into the URL fragment (never sent to servers); applySetupLink() consumes it on boot and strips the fragment so the key doesn't linger in the address bar. includeAI:false variant omits AI keys. One tap configures a whole device.
Honesty: the open policy means anyone with the link reads every record — fine for seeded demo data, NOT for real patients. Warn in-app. Records subtitle says "local-first, then sync"; consent script says results are shared with the programme.
Critical wiring in app.js: the sync listener refreshes the current view on a completed pull — but guard it hard: never re-render while the screening flow is open, while an input is focused, or while a sheet is open. Re-rendering the form mid-entry destroys the user's typing and wipes a freshly generated referral slip. This is the single nastiest bug in the app; get the guard right.
